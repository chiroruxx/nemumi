# コンテンツ自動更新

**ステータス: 実装中（ローカル実装済み、初回運用確認待ち）**

## 概要

各種サービスでコンテンツが更新された際に、自動でこのサイトのコンテンツも更新する。
更新はリアルタイムである必要はない。
RSSを用いて更新の確認を行う。

各種コンテンツとサービスの対応は以下である。
サービスなしのものは手動で更新するとして、このプロジェクトでは対象としない。

| サイトコンテンツ | 種別       | サービス               | サービスサイト                    |
|------------------|------------|------------------------|-----------------------------------|
| activities       |            | なし                   |                                   |
| articles         | 日常記事   | しずかなインターネット | https://sizu.me/chihiroxx         |
| articles         | テック記事 | はてなブログ           | https://toyo.hatenablog.jp        |
| communities      |            | なし                   |                                   |
| talks            | 登壇資料   | SpeakerDeck            | https://speakerdeck.com/chiroruxx |

## 計画の状態

概要、既存コード、3サービスの RSS を確認して計画を作成し、同期・削除スクリプトと GitHub Actions ワークフローを実装中。GitHub
App の登録、初回 PR の確認、本番運用の確認は未完了。
共通の設計方針は [ADR 0025](../adr/0025-sync-external-content-from-rss.md) に記載する。

以下の運用条件は確認済み。ローカル実装とワークフロー定義を追加済みで、外部設定と運用確認を進める。

| 項目           | 決定内容                                                                    | 状態     |
|----------------|-----------------------------------------------------------------------------|----------|
| 公開方法       | 初回は手動確認・マージし、通常運用は必須 CI 成功後に自動マージする          | 確認済み |

| 保持件数       | `articles` は最大20件、`talks` は最大10件。サービスごとの枠は設けない       | 確認済み |

### 実装時に確認する環境設定

利用方針について追加の確認待ちはない。実装時に以下の環境設定とサービス応答を確認する。

- GitHub App の用意と、対象リポジトリへのインストール・権限・Actions Secret の設定。
- リポジトリの auto-merge 有効化、必須チェック、レビュー条件、許可されたマージ方法との整合。
- 3サービスの削除・非公開時の応答と表示。識別できない応答は判定保留とする。

## 対象と完了条件

- しずかなインターネット、はてなブログ、Speaker Deck の公開 RSS から、記事・資料の新規追加と掲載情報の更新を取り込む。
- 取り込む情報は公開日、タイトル、リンク先 URL、種別とする。本文、概要、画像、サービスのカテゴリは取り込まない。
- ディレクトリごとの上限内で保持する対象サービスのリンクを定期確認し、削除・非公開を確認できた項目を掲載データから除去する。
- `activities`、`communities`、対象サービス以外の手動データは自動更新しない。
- 更新確認から公開までの流れを GitHub Actions と既存の Cloudflare Workers Builds に接続する。
- 同じ RSS で再実行しても、重複ファイル・不要なコミット・不要な PR が発生しない。
- `articles`・`talks` の保持数をそれぞれの上限以内にし、上限超過による削除は別の削除 PR に含める。
- RSS の取得・検証に失敗したサービスは更新せず、他サービスの更新は継続する。削除は実行時点の最新
  main を対象とする。個別リンクの一時的な確認失敗は削除の根拠にしない。
- 本番で新しい記事または資料の反映を確認し、運用手順を README に記載した時点で完了とする。

## 現状

- `src/content.config.ts` は `articles` と `talks` の YAML を `glob()` で読み込む。
- 両コレクションの項目は `date`、`title`、任意の `types`、任意の `url` で構成される。
- 既存ファイル名は日付と連番であり、URL を読み込んで既存項目との対応を判定する必要がある。
- トップページは記事と活動を合わせて新しい順に10件、登壇資料を新しい順に5件表示する。取得件数を表示件数で制限しない。
- PR と `main` へのプッシュで既存 CI が動作し、`main` へのプッシュで本番ビルド・デプロイが動作する。
- ページのテストは `tests/fixtures/content` を使う。同期処理のテストも実サービスの応答から独立させる。

## RSS と項目の対応

2026-10-13 に以下の URL への HTTP 200 応答と RSS の項目を確認した。取得できた件数は確認時点の値であり、配信上限を示すものではない。

| サービス               | RSS                                   | 保存先                  | 新規項目の `types` | 確認時の件数 |
|------------------------|---------------------------------------|-------------------------|--------------------|--------------|
| しずかなインターネット | https://sizu.me/chihiroxx/rss         | `src/content/articles/` | `["日常記事"]`     | 24           |
| はてなブログ           | https://toyo.hatenablog.jp/rss        | `src/content/articles/` | `["テック記事"]`   | 30           |
| Speaker Deck           | https://speakerdeck.com/chiroruxx.rss | `src/content/talks/`    | `["登壇資料"]`     | 18           |

| YAML 項目 | RSS 項目     | 変換・検証                                                                  |
|-----------|--------------|-----------------------------------------------------------------------------|
| `date`    | `pubDate`    | タイムゾーン付き日時を解析し、`Asia/Tokyo` の日付を `YYYY-MM-DD` で保存する |
| `title`   | `title`      | XML パーサでエンティティを復号し、前後の空白を除く。空白だけの値はエラー    |
| `url`     | `link`       | HTTPS、サービスのホスト、対象アカウントのパスを検証する                     |
| `types`   | サービス設定 | 新規項目には表の値を設定する。既存項目の手動設定は保持する                  |

`guid` はサービスごとに形式が異なる。はてなブログでは公開 URL と異なるため、項目の照合には `link` を使う。
公開日が欠落・不正な場合、実行日や更新日時で代用せず、その実行を失敗とする。

## 同期処理

### 取得と検証

1. 3サービスの固定 RSS URL を取得する。各リクエストのタイムアウトは30秒、応答サイズの上限は5 MiB とする。
2. ネットワークエラー、HTTP 429・5xx は最大2回再試行する。HTTP 429 の `Retry-After` は実行時間の上限内で扱う。
3. XML はパーサで解析し、外部エンティティを解決しない。本文の HTML は取得結果から保存しない。
4. 各項目のタイトル・公開日・URL を検証する。想定外のホストや対象アカウント外の URL はエラーとする。
5. サービスごとに取得結果と既存 YAML を検証する。成功したサービスの追加・更新を独立した PR に反映し、失敗したサービスの PR
   は更新しない。

空のフィードは既存項目の削除に使わず、警告を出す。RSS の構造変更、解析失敗、同じ URL に異なる内容がある場合はエラーとする。

### 重複判定と保存

- 比較用 URL はフラグメントを除き、URL パーサで正規化する。パス・クエリを一律に削除したり、小文字に変換したりしない。
- 対象コレクション内の既存 YAML を読み込み、比較用 URL からファイルへの対応表を作る。既存データに同じ URL
  が複数あれば自動処理を停止し、手動で解消する。
- 既存 URL に一致する場合は元のファイルを更新する。ファイル名と `types`、その他の手動管理項目は保持し、`date`・`title`・
  `url` を同期する。
- 新規項目のファイル名は `<source>-<比較用URLのSHA-256>.yaml` とする。`source` は `sizu`、`hatena`、`speakerdeck`
  とし、日付・タイトル変更でファイル名を変えない。
- SHA-256 は省略せず64桁の小文字16進数を使う。同名ファイルが別 URL に対応する場合は上書きせずエラーとする。
- 件数制限の並び順は YAML の `date` と比較用 URL で判定し、ファイル名の順序や連番には依存しない。削除後も他のファイルを改名せず、同じ
  URL の再取り込みでは同じ新規ファイル名を生成する。
- 削除・変更対象を人が確認できるよう、dry-run と PR 本文にはファイル名に加えて公開日・タイトル・URL を記載する。
- URL が変更された場合は新規項目として扱う。旧 URL との統合は手動で対応する。
- YAML はシリアライザで出力し、引用符・改行・コロンを含むタイトルも文字列として保存する。
- 値が変わらない既存ファイルは書き直さない。項目の順序や RSS の取得日時だけでは差分を作らない。
- RSS
  に存在しないことだけでは削除しない。掲載データの除去は保持件数の上限とリンク先確認の結果で判断する（[ADR 0025](../adr/0025-sync-external-content-from-rss.md)）。

### ディレクトリごとの保持件数

| ディレクトリ            | 保持数   | 選び方                                                                     |
|-------------------------|----------|----------------------------------------------------------------------------|
| `src/content/articles/` | 最大20件 | しずかなインターネットとはてなブログの記事を合わせ、公開日の新しい順に選ぶ |
| `src/content/talks/`    | 最大10件 | 登壇資料を公開日の新しい順に選ぶ                                           |

- 上限の単位はディレクトリとし、サービスごとの件数配分は設けない。
- 既存データと RSS の全項目を URL で照合・統合してから保持対象を選ぶ。RSS の並び順ではなく `date` の降順、同日の場合は比較用
  URL の昇順で決める。
- 上限を超える古い対象サービスの YAML はリンク確認せず、上限超過を理由として削除 PR で削除する。RSS
  に残っていても、保持対象に選ばれない項目は再追加しない。
- 対象サービス以外の手動データもディレクトリの件数に含めるが、自動削除しない。その件数を上限から引いた残りを同期対象の枠とする。手動データだけで上限を超える場合はエラーとし、手動整理する。
- 保持対象を選んだ後に、その対象サービスの URL だけリンク確認する。確認する URL
  は削除処理1実行で最大30件とする（リダイレクト等による追加リクエストを除く）。
- 無効リンクの除去で上限未満になっても、その実行では上限外の項目を追加確認して補充しない。
- 件数の上限は保存する YAML に適用する。トップページの表示件数は現在のままとする。

### リンク先の確認と掲載データの除去

- 保持対象に選んだ、対象サービス・アカウントの既存 URL と RSS から新しく取得した URL を確認する。RSS
  配信範囲外の過去項目も、保持対象であれば確認する。
- `GET` で公開状態を確認する。タイムアウトは30秒、同時リクエストは最大2件とし、同じサービスへの連続アクセスには1秒以上の間隔を置く。
- 判定は次の表に従う。サービス固有の非公開表示や HTTP 200 のエラーページは、Step 1 で実例・仕様を確認して識別できたものだけ判定する。

| 応答・状態                                                         | 掲載データの扱い                                                                                                                                         |
|--------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| 公開ページを確認できる                                             | 保持する                                                                                                                                                 |
| 対象 URL が直接返す HTTP 404・410、検証済みの削除・非公開表示      | その削除処理の実行で YAML の削除を削除 PR に含める                                                                                                       |
| HTTP 401・403・429・5xx、タイムアウト、接続失敗、判別できない HTML | 判定保留として保持し、警告を出す。自動削除しない                                                                                                         |
| リダイレクト                                                       | 遷移先を検証して最大5回まで確認する。対象アカウントのコンテンツ URL への遷移は最終応答で判定する。トップ・ログインページ・別ホストへの遷移は手動確認する |

- 404・410 または検証済みの削除・非公開表示を確認したら、その削除処理の実行で YAML の削除を削除 PR に含める。初回実行も同じ判定とする。
- RSS に残る項目もリンク確認結果を優先し、確認済みの無効 URL を追加・再追加しない。再公開を確認でき、RSS にも含まれる場合は再取り込みする。
- 未マージの削除 PR がある場合も再確認する。公開状態に戻った項目や判定保留になった項目の削除差分は取り消す。
- 上限超過による削除は公開状態にかかわらず保持件数のルールで判断する。判定保留も上限内の項目として扱い、実行間で状態を保存せずログに記録する。
- 全 URL を実行時間内に確認できない場合は未確認項目を保持し、次回へ繰り越す。

### 初回実行

- 初回も RSS の全項目と既存データを照合・統合し、上限内の保持対象を選ぶ。RSS 配信範囲外の過去データも保持対象であれば残す。
- 過去の全記事・資料の取得、未登録 URL を探す HTML の巡回、API による履歴取得は対象外とする。登録済みリンクの公開状態確認は行う。
- 初回は dry-run で追加・変更件数、リンク確認結果と差分を確認し、重複や日付変換の不整合を解消する。削除対象も差分に表示する。
- 初回のサービス別取り込み PR と削除 PR は手動で確認・マージし、その後に選択した通常運用へ切り替える。

## GitHub Actions と公開

自動更新処理は次の4種類に分け、未マージの自動更新 PR は最大4つとする。サービスごとの削除 PR は作らない。
各 PR には既存の必須 CI が実行されるため、GitHub Actions の実行総数が4回に限定されるわけではない。

| 処理              | PR                        | 開始条件                 |
|-------------------|---------------------------|--------------------------|
| しずかな同期      | しずかな同期 PR           | 定期・手動実行で並列開始 |
| はてな同期        | はてな同期 PR             | 定期・手動実行で並列開始 |
| Speaker Deck 同期 | Speaker Deck 同期 PR      | 定期・手動実行で並列開始 |
| 上限オーバー削除  | 共通の上限オーバー削除 PR | 毎日 JST 07:17           |

差分がない処理では PR を作らない。共通の削除処理には、以下で定義する無効リンクの除去も含める。

### サービス別の並列実行と PR

- `.github/workflows/update-content.yml` を追加し、定期実行の `schedule` と手動実行の `workflow_dispatch` を用意する。
- 1日1回、cron `17 21 * * *`（UTC、JST 06:17）で実行する。
- サービス処理は matrix で並列実行する。`fail-fast: false` とし、1サービスの失敗で他サービスを中断しない。
- RSS 取得を並列に実行した後、取得結果と既存データからディレクトリ全体の保持候補を選ぶ。成功したサービスごとに候補の追加・更新
  PR を並列に作成し、それぞれで既存 CI を実行する。
- 取得失敗したサービスの変更は反映せず、成功したサービスの PR 作成・CI・マージは進められる。削除処理は全サービスの成功を照合せず、最新
  main を対象とする。
- サービス別ジョブは自分のサービスの追加・変更だけを扱い、削除・ディレクトリ全体の件数整理は行わない。同じ `articles`
  ディレクトリを扱う場合も URL で変更対象を限定する。
- 新規 URL は追加前にリンク確認し、404・410 等と確認できたものは追加しない。保持対象外の RSS 項目も追加しない。既存項目の削除は後段へ回す。
- 更新ブランチは `automation/update-sizu`、`automation/update-hatena`、`automation/update-speakerdeck` とし、サービスごとに未マージ
  PR を1つまで維持する。
- 変更がないサービスは PR を作らない。差分があればサービス別 PR を作成・更新する。
- 定期・手動の再実行では各サービスを同期し、未マージの PR があれば同じ PR を更新する。競合やベース更新が必要な場合は最新
  `main` に合わせて再生成し、変更後の
  head に対する必須 CI を実行する。
- Node.js・pnpm は既存 CI と同様に mise で用意し、依存関係は `--frozen-lockfile` でインストールする。
- 各取得・PR 生成ジョブのタイムアウトは10分とする。手動マージを待つために runner を起動し続けない。
- 同期と削除のワークフローに共通の `concurrency` グループを設定し、PR 生成の重複を防ぐ。実行中の処理はキャンセルせず、サービス別ジョブは同じ同期実行内で並列に動かす。
- ブランチは自動処理専用とし、想定外の手動変更は上書きせず停止する。PR を手動で閉じた場合は該当サービスの自動処理を停止し、運用担当者が再開方法を判断する。

### 時間をずらした削除処理

- `.github/workflows/prune-content.yml` を追加し、1日1回、cron `17 22 * * *`（UTC、JST 07:17）で実行する。手動実行も提供する。
- 同期との時間差は1時間とする。実行サイクルや全サービスの成功・マージ完了を Artifact
  で管理せず、マージイベントによる自動起動も行わない（[ADR 0025](../adr/0025-sync-external-content-from-rss.md)）。
- 未マージの同期 PR の有無にかかわらず、削除処理を実行する。PR のブランチ上の変更は削除対象に含めない。削除後にマージされた変更は次回の削除処理で整理する。
- 時間差は同期の完了を保証しない。取得失敗などで同期 PR が作られなかった場合も、削除は実行時点の最新 `main` を対象とする。
- 同期・削除の PR 生成は共通の `concurrency` で直列化する。当日の同期が削除より先に実行されたことまでは保証しない。
- 最新 `main` でディレクトリ別の上限を適用し、上限外の項目を削除する。保持対象のリンク確認で無効と判定した項目も削除する。
- `automation/prune-content` ブランチと共通の削除 PR を1つまで維持する。再実行では最新 `main` から再計算して同じ PR
  を更新する。
- PR 本文に削除理由、公開日・タイトル・URL、ディレクトリ別の残件数を記載する。既存の必須 CI を実行し、差分がなければ PR
  を作らない。
- 未マージの削除 PR があっても同期側の PR 作成・更新を進める。削除の再実行では同じ PR を更新し、差分がなくなれば閉じる。
- 同期 PR のマージや手動変更で `main` が変わった場合は、削除の再実行で差分を再計算し、更新した PR の CI を再実行する。
- 同期 PR のマージから削除 PR のマージまでは保存件数が一時的に上限を超える。各マージで本番デプロイが動作する。

### 認証とマージ

- PR 作成・更新には、対象リポジトリだけにインストールした GitHub App の installation token
  を使う（[ADR 0025](../adr/0025-sync-external-content-from-rss.md)）。
- GitHub App の権限は `Contents: Read and write`、`Pull requests: Read and write` とする。ルールセットの bypass 権限は付与しない。
- App ID と秘密鍵を Actions の設定に登録する。秘密鍵は Secret とし、ログや PR 本文に出力しない。
- 既存 CI の Lint・型チェック・テスト・ビルドと Lighthouse CI をサービス別 PR と削除 PR それぞれで実行する。
- リポジトリの auto-merge 設定、必須チェック、レビュー条件、許可されたマージ方法を確認する。条件が成立しない場合は
  PR を保持して停止し、ルールを回避しない。
- 自動マージを設定する対象は、App が作成したサービス別 PR または削除 PR で、変更パスの検証に成功したものだけとする。
- 初回は PR の CI 成功後に運用担当者が差分を確認して手動マージする。通常運用では自動マージを設定する。
- マージ後は既存の Workers Builds でビルド・デプロイし、本番ページの表示まで確認する。

## 検証項目

| ケース                                                         | 期待する結果                                                                 |
|----------------------------------------------------------------|------------------------------------------------------------------------------|
| 各サービスの新規項目                                           | 正しい保存先・種別・公開日で1件追加される                                    |
| 同じ RSS の再実行・項目順の変更                                | 差分が発生しない                                                             |
| 既存 URL のタイトル・公開日変更                                | 元のファイルを更新し、手動の種別を保持する                                   |
| 同日・同名の別 URL                                             | 別項目として保存される                                                       |
| JST の日付境界・Speaker Deck の時差                            | 想定した `YYYY-MM-DD` になる                                                 |
| XML エンティティ・引用符・改行入りタイトル                     | YAML 読み込み後も正しい文字列になる                                          |
| RSS 配信範囲外だが公開中で上限内の既存項目・対象外の手動データ | 保持される                                                                   |
| 複数サービスを含む `articles` が上限を超える                   | サービスの配分を設けず公開日順で保持し、古い対象項目の削除を削除 PR に含める |
| 同日の項目・RSS の並び順変更                                   | 比較用 URL で順序を固定し、保持対象が変動しない                              |
| 上限外の項目が RSS に残る                                      | YAML の再追加もリンク確認も行わない                                          |
| 手動データが同じディレクトリにある                             | 自動削除せず、その件数を引いた枠で同期対象を保持する                         |
| 手動データだけで上限を超える                                   | エラーとなり、自動で手動データを削除しない                                   |
| 保持対象のリンクが無効                                         | 削除を削除 PR に含め、その実行では上限外の項目を補充しない                   |
| 404・410 または検証済みの削除・非公開表示（初回を含む）        | その削除処理の実行で YAML の削除を削除 PR に含める                           |
| リンク先の403・429・5xx・タイムアウト・判別不能な200           | 判定保留として保持し、警告を出す                                             |
| 未マージの削除項目が再公開される                               | 削除差分を取り消す                                                           |
| 無効と確認済みの URL が RSS に残る                             | 追加・再追加しない                                                           |
| タイムアウト・429・5xx・壊れた XML・必須項目不正               | 再試行条件を守り、失敗時は公開用の差分を書き込まない                         |
| 重複 URL・対象外 URL・想定外の変更パス                         | エラーとなり PR を作成・更新しない                                           |
| dry-run                                                        | 変更予定を表示し、ファイル・Git・GitHub を変更しない                         |
| 未マージ PR がある状態で再実行                                 | 同じ PR を更新し、必須 CI が再実行される                                     |
| 当該 PR の CI 失敗・マージ条件未達                             | 本番へ反映されない                                                           |

並列同期と時間をずらした削除では、次のケースも検証する。

| ケース                                 | 期待する結果                                             |
|----------------------------------------|----------------------------------------------------------|
| サービスの取得が失敗する               | 他サービスの同期を進め、削除は最新 main を対象に実行する |
| 未マージの同期 PR がある               | 最新 main を整理し、未マージの変更は含めない             |
| 同期 PR がなく、削除の実行時刻になった | 最新 main を整理する                                     |
| 同期と削除のワークフローが重なる       | 共通の concurrency で PR 生成を直列化する                |
| 未マージの削除 PR がある               | 同期は進め、削除の再実行では同じ PR を更新する           |
| 削除した古い項目が RSS に残る          | 保持対象でなければ再追加しない                           |

ページの既存 fixture テストを維持し、実装後は `mise run test` と本番用 `mise run build` も実行する。

## 運用

- 実行結果にサービス別の取得・追加・変更・削除・判定保留件数、PR の URL、失敗箇所を記録する。取得日時をコンテンツファイルへ保存しない。
- GitHub Actions の失敗通知を確認できるようにし、失敗時はログを確認して `workflow_dispatch` で再実行する。
- 取得・解析エラー時は RSS の応答と仕様を確認する。CI エラー時は PR の差分とチェック結果を確認し、修正後に再実行する。
- 本番デプロイ失敗時は Workers Builds のログを確認する。`main` の更新だけで公開完了とは扱わない。
- 誤った更新は該当コミットを revert して再デプロイする。再取り込みを防ぐため、必要に応じて同期ワークフローを無効化して修正する。
- 手動で削除した URL が RSS に残っている場合は次回同期で再追加される。継続的な除外が必要な場合は除外リストの設計を別途行う。
- リンク確認で判別できない非公開状態やエラーページ、リダイレクトは手動で公開状態を確認し、掲載データを修正する。
- RSS 配信範囲外のタイトル等の更新、長期間停止中に RSS から外れた項目の追加は自動検出の対象外とする。
- 定期実行の遅延・停止を確認し、公開リポジトリで無活動による自動停止が起きた場合はワークフローを再有効化する。
