# ローカルレビュー

新しい文脈で独立したレビュー担当を使う。名前付きの `local-reviewer`
エージェントを選べる場合はそれを使う。選べない場合は、利用中のクライアントのモデル設定に従って新しいサブエージェントを起動し、この手順書の基準に従う
`local-reviewer` の役割と、ファイルを編集せず指定範囲だけをレビューすることを明示する。実装担当自身のレビューで独立レビューを代用しない。
1. 文書をレビューするときは、完成した文書、関連する決定、範囲の評価に必要な背景を渡す。重要な要件文書は実装開始前に、ADR
   は作成・変更後かつ PR 作成前に実施する。ADR を含むレビューでは [ADR テンプレート](../../../docs/adr/template.md)
   を読み、テンプレートへの準拠も確認する。
2. コードをレビューするときは、PR stack
   で直前のPRをベースとする機能単位の差分、要件の根拠、関連する呼び出し元とテストを渡す。レビュー対象に含める場合に限り、未コミット・未追跡の変更も含める。機能が完成し、PR
   を準備する前に実施する。整形のみの変更は対象外とし、PR stack 内の以前の変更を再レビューしない。
3. この手順書を読み、関連するコード経路だけを調べ、ファイルを編集せず根拠に基づいて指摘するようレビュー担当に依頼する。
4. 各指摘を実際の要件と振る舞いに照らして確認する。必要な問題だと確認できたものだけを修正し、任意の簡素化案は実装者の判断に委ねる。

## レビュー基準

渡された範囲から確認できる次の点だけを評価する。文書の種類に応じて適用する基準を選び、要件文書に限る分類基準を ADR
など他の文書に強制しない。
- 要件文書の振る舞いが必須要件・未採用候補・実装裁量に明確に分類され、変更が必須要件を保っているか。
- ADR のタイトル、ステータス、決定日、見出しがテンプレートに沿い、選択肢が表形式で採択案を太字にして評価され、結果（良い点・注意点）が記載されているか。既存
  ADR の決定日を更新日で上書きしておらず、設計上の決定と背景・理由が説明され、機能仕様や具体的な設定値・処理手順が ADR
  に混在していないか。
- 共通処理が、似た関数シグネチャや名前だけでなく、実際の値と呼び出し経路で裏付けられているか。
- 標準 API や既存の依存関係で要件を満たせるか。
- 契約変更後に不要な変換、検索、検証、設定、返却値、エクスポート、補助関数が残っていないか。
- テストが内部実装をなぞらず、観測可能な契約を保護しているか。また、テストのためだけにエクスポートを追加していないか。

具体的な問題を根拠で示せる場合だけ指摘する。ファイルと行、発生条件、影響を受ける要件または振る舞い、影響を記載し、次のいずれかに分類する。
- **必須修正（Required correction）**
- **任意の簡素化（Optional simplification）**

根拠に該当する問題がなければ、指摘なしと報告してよい。呼び出し元が一つという理由だけで抽象化に反対しない。
`sameContent` のような有用な名前や、意味のある境界を保つ1行のアダプターは維持できる。スタイル上の好みや将来に関する推測を欠陥として扱わない。

## この手順書の評価

レビューの振る舞いを評価するときは、[評価用の指示文](references/evaluation-prompts.md)
と[個別の期待結果](references/evaluation-expectations.md)
を読む。各回でレビュー担当に渡すのは、1つの指示文と、その対象となるコードまたは文書だけにする。期待結果ファイルはレビュー担当に渡さない。
