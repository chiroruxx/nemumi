# Lighthouse CI でサイト品質を検査する

- **ステータス**: 承認
- **決定日**: 2026-10-10

## 背景

Lighthouse の計測は手動では継続しにくく、変更によるパフォーマンスやアクセシビリティなどの劣化を見逃す可能性がある。サイトは静的にビルドされるため、デプロイ前のビルド成果物を
CI で検査できる。

## 決定

- Lighthouse CI を GitHub Actions の独立したジョブとして追加し、PR と `main` へのプッシュ時に通常の CI と並列で実行する。
- 本番環境ではなく、CI が生成した `dist/` をモバイル条件で検査する。
- CI で Chrome を起動するために `--no-sandbox` を指定し、モバイルのシミュレーション条件を明示する。
- 計測を3回行い、カテゴリスコアと主要なパフォーマンス指標は中央値で判定する。
- 初期の基準は現在の計測結果をもとに余裕を設けて設定し、詳細は `lighthouserc.json` に定義する。
  - Performance 70点以上、Accessibility と SEO は100点、Best Practices は95点以上。
  - FCP・LCP・Speed Index は5秒以下、TBT は200ms以下、CLS は0.1以下。
- Lighthouse レポートを GitHub Actions Artifact として14日間保存する。
- Lighthouse CI のジョブをマージ必須チェックにする場合は、リポジトリのルールセットにも設定する。

## 検討した選択肢

| 選択肢                        | 評価                                                                   |
| ----------------------------- | ---------------------------------------------------------------------- |
| **Lighthouse CI の固定基準**  | 実行環境で再現でき、しきい値を超える劣化をマージ前に検出できる         |
| PR とベースブランチの差分比較 | 小さな環境差や計測の揺れを劣化と誤判定しやすく、初期設定と保守も増える |
| 手動計測のみ                  | 継続的な確認が必要で、変更のたびに実行する保証がない                   |

## 結果

- **良い点**
  - 主要カテゴリと指標の基準割れをマージ前に検出できる。
  - レポートを後から確認して、失敗した監査項目を調べられる。
- **注意点**
  - 固定基準による検査のため、しきい値を下回らない小さな悪化は失敗にならない。
  - Performance は計測環境で変動するため、3回の中央値で判定する。
  - 独立したジョブで依存関係のインストールとビルドを行うため、GitHub Actions の実行時間が増える。
