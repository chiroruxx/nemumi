# 外部コンテンツを RSS から同期する

- **ステータス**: 承認
- **日付**: 2026-10-13

## 背景

記事と登壇資料は外部サービスで公開しており、サイト側ではリンクと公開日を YAML で手動管理している。
リアルタイム反映は不要であり、3サービスが配信している RSS を使って定期的に更新を取り込む。

既存サイトは SSG
であり、コンテンツは1件につき1ファイルで管理している（[Astro Content Collections によるコンテンツデータの管理](2026-09-25-content-collections.md)）。
取得済みの内容を Git に保持すれば、外部サービスの一時的な障害中も既存データでビルドでき、差分を PR で確認できる。

RSS は全履歴を配信する保証がないため、フィードに存在しないことだけでは削除・非公開と判定できない。
一方で、無効なリンクを掲載し続けないため、登録済み URL の公開状態も定期確認する。
ページが見つからないと確認できた項目は、その実行で削除対象とし、判定を実行間で持ち越さない。
アクセス制限や一時障害はページの不存在とは区別し、判定保留とする。
また、公開日のタイムゾーンがサービスごとに異なるため、保存する日付の基準を統一する必要がある。

コンテンツの増加に伴って全 URL の確認リクエストが増えるため、保存する件数に上限を設ける。
記事と登壇資料はディレクトリごとに一覧を構成しているので、保持件数もディレクトリ単位で管理する。

サービスごとの更新と CI を並列に進めるため、更新 PR はサービス単位に分ける。
記事の上限はサービスをまたぐため、削除は共通処理とする。
リアルタイム更新は不要なので、同期より1時間遅い時刻に削除を定期実行し、その時点の main を整理する。
運用を簡単にするため、全サービスの当日の成功・マージ完了を Artifact で追跡しない。時間差は同期の完了を保証せず、削除は未マージ
PR の有無にかかわらず実行時点の main だけを対象とする。

保持対象の順序は YAML の公開日から判定できるため、ファイル名に日付や順位を持たせる必要はない。
URL 由来の固定名にすると、公開日・タイトルの変更や他の項目の削除で改名が発生せず、再取り込み時にも同じ名前を生成できる。
変更と削除は PR diff で確認する。

GitHub の公式ドキュメントでは、`GITHUB_TOKEN` で作成・更新した PR のワークフローに実行承認が必要になる場合がある。
人の承認なしで既存 CI を実行できるよう、PR の操作には GitHub App の installation token を使う。
根拠は [GitHub のワークフロー起動の説明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)
を参照する。

## 決定

### 同期対象と取得方法

- GitHub Actions で、しずかなインターネット、はてなブログ、Speaker Deck の RSS を定期取得する。手動実行も提供する。
- 定期取得は1日1回、JST 06:17（UTC の cron `17 21 * * *`）に実行する。
- 取得処理をビルドから分離し、`articles`・`talks` の既存形式の YAML に追加・更新する。本文や画像は同期しない。
- 手動管理の活動・コミュニティ・対象サービス以外のデータは同期対象外とする。

### 項目の照合とファイル管理

- 公開 URL を項目の照合キーとし、既存ファイルを保持する。新規ファイルにはサービス名と URL の SHA-256 を使う。
- SHA-256 は64桁の小文字16進数を使う。削除に伴う連番の振り直しや改名は行わない。
- 公開日時はサイト設定のタイムゾーン（[サイトのタイムゾーンを一元管理する](2026-10-14-site-time-zone.md)）の日付に変換する。Speaker
  Deck も RSS の公開日を使う。
- サービスに対応する種別は新規項目へ設定し、既存項目の手動の種別は保持する。

### 保持件数と上限超過の整理

| ディレクトリ | 保持件数 |
|--------------|----------|
| `articles`   | 最大20件 |
| `talks`      | 最大10件 |

- 同期は既存データと RSS を照合し、削除は保存済みデータだけから公開日順で保持対象を選ぶ。サービスごとの枠は設けない。
- 上限による選定は YAML の公開日が新しい順で行い、同日なら比較用 URL（URL がない項目はファイルパス）の順で決める。
- `articles`・`talks` の保存済み YAML は手動・自動管理を区別せず保持件数を適用し、上限を超える古い項目は共通の削除 PR
  に含める。
- 保存件数の上限は削除 PR のマージ後に満たし、中間状態では一時的な超過を許容する。

### 無効リンクの判定と除去

- 保持対象の登録済み URL と RSS の新規 URL を定期確認する。RSS の欠落だけでは削除しない。
- 保持対象の URL だけリンク確認し、無効リンクの削除で上限未満になっても同じ実行内で上限外の項目を補充しない。

| 確認結果                                                | 扱い                                                       |
|---------------------------------------------------------|------------------------------------------------------------|
| 404・410 または検証済みのサービス固有の削除・非公開表示 | その実行で共通の削除 PR に含める。初回実行も同じ判定とする |
| 一時障害・アクセス制限・判別不能な応答                  | 判定保留として保持する                                     |
| 未マージの削除項目が公開成功・判定保留となった場合      | 削除差分を取り消す                                         |

判定保留は永続化しない。

### サービス別 PR と実行順序

| 処理                         | PR                  | 実行タイミング      |
|------------------------------|---------------------|---------------------|
| しずかなインターネットの同期 | サービス別の同期 PR | 3サービスを並列実行 |
| はてなブログの同期           | サービス別の同期 PR | 3サービスを並列実行 |
| Speaker Deck の同期          | サービス別の同期 PR | 3サービスを並列実行 |
| 上限超過・無効リンクの除去   | 共通の削除 PR       | 毎日 JST 07:17      |

- 未マージの自動更新 PR は最大4つとし、差分がなければ作らない。サービスごとの削除 PR は作らない。
- 同期 PR の CI も並列実行する。失敗したサービスは更新せず、他サービスは進行できる。
- 同期は JST 06:17、削除は1時間後の JST 07:17（UTC の cron `17 22 * * *`）に定期実行する。手動実行も提供する。
- 削除は実行時点の最新 main を対象とし、全サービスの成功や当日の同期が先に実行されたことを前提にしない。
- サイクル ID・完了状態を Artifact で管理せず、マージイベントからも起動しない。
- 未マージ PR を理由として同期・削除を見送らない。未マージの同期結果は削除対象に含めず、後からマージされた変更は次回の削除処理で整理する。
- 同期・削除の PR 生成は共通の concurrency グループで直列化し、既存の PR を再利用する。

### 認証・マージ・公開

- PR の操作には、このリポジトリに限定した GitHub App を使う。ルールセットの bypass 権限を付与しない。
- 各同期 PR と共通の削除 PR は、既存の必須 CI とマージ条件を満たしてから `main` に反映する。
- 通常運用は必須 CI 成功後に自動マージする。初回の取り込みは手動で確認・マージする。
- 既存の Workers Builds で各マージを公開する。

## 検討した選択肢

| 選択肢                                     | 評価                                                                             |
|--------------------------------------------|----------------------------------------------------------------------------------|
| **定期取得して YAML を更新する PR を作る** | 既存の SSG・データ形式・CI を利用でき、変更履歴と取得済みデータを保持できる      |
| ビルド時に RSS を直接取得する              | 定期ビルドが必要で、毎回のビルドが外部サービスに依存する。履歴保持の仕組みも必要 |
| 閲覧時に RSS を取得する                    | 閲覧時の外部通信と動的処理が必要になり、既存 SSG の構成から変更が増える          |
| 手動更新を継続する                         | 新たな仕組みは不要だが、自動更新の目的を満たさない                               |

| PR 操作の認証                     | 評価                                                                |
|-----------------------------------|---------------------------------------------------------------------|
| **GitHub App installation token** | 対象リポジトリと権限を限定でき、PR の CI を承認操作なしで起動できる |
| `GITHUB_TOKEN`                    | 追加の認証管理は少ないが、PR の CI に承認操作が必要になる場合がある |
| Personal access token             | CI を起動できるが、個人アカウントに依存する認証情報の管理が必要     |

## 結果

- **良い点**
    - 外部サービスの新規公開と RSS 内の変更を、既存のコンテンツ管理・公開フローに接続できる。
    - 外部サービスの障害時も最後に取り込んだ内容を保持できる。
    - 変更履歴を Git で管理し、誤更新を revert できる。
- **注意点**
    - RSS 配信範囲外のタイトル等の変更・長期停止中の新規項目は検出できない。
    - 無効なリンクの除去は共通の削除 PR のマージ後に公開される。
    - 公開状態を識別できない応答は手動確認が必要になる。
    - RSS 取得に加えて、上限内の保持対象 URL の確認リクエストが必要になる。
    - 上限を超える古い項目は公開中でもサイトの YAML から除去する。サービスごとの掲載数は一定にならない。
    - URL の変更は新規項目として扱われ、旧項目との統合は手動対応になる。
    - 手動のタイトル・公開日・URL の変更は次回同期で上書きされる。
    - GitHub App の秘密鍵とワークフローの運用が必要になる。
    - サービス別 PR と削除 PR にそれぞれ CI・デプロイが発生する。全変更は一括公開されず、件数が一時的に上限を超える。
    - 時間差は同期の完了を保証しない。取得失敗・実行遅延・未マージの同期 PR がある場合も、その時点の main
      を整理する。後からマージされた変更の整理は次回の削除まで遅れる場合がある。
    -
  定期実行には遅延があり、公開リポジトリでは60日間の無活動で停止することがある（[GitHub Actions の schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)）。
