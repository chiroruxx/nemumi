## 優先度と確認状況

| 表記 | 意味 |
|---|---|
| P1 | 自動更新・削除を運用する前に対応または仕様を確定したい |
| P2 | 責務分離・テスト・運用上の保守性を改善する |
| P3 | 上記の整理後に必要性を判断する |
| 再現済み | 比較先のコードを一時ディレクトリで実行して挙動を確認した |
| コード確認 | 実装・テストから確認した。該当する異常系の実行確認はしていない |

## 先に扱う挙動と境界

### 01. リダイレクト先をコンテンツ URL として検証する

- **P1 / 不具合修正 / 再現済み**
- 対象: [external-content.ts:351](https://github.com/chiroruxx/nemumi/blob/957c922e39d330f99bb5d1abcc42525ffd55a5ac/scripts/lib/external-content.ts#L351)、`verifyLink`。
- 現状: 遷移先の HTTPS とホストだけを確認し、対象アカウント・コンテンツのパスを確認しない。
  `/login` へ転送されて 200 を返すと `public`、404 を返すと `deleted` になる。後者は元コンテンツの削除根拠になってしまう。
- 改善案: コンテンツ URL の検証を各遷移先にも適用し、トップ・ログイン・対象外アカウントへの遷移は `review` にする。
- 完了条件: 相対 Location、同一アカウントへの転送、ログイン、別アカウント、別ホスト、循環、5 回超過をテストする。

### 02. RSS 内の重複 URL を計画作成前に解消・拒否する

- **P1 / 不具合修正 / 再現済み**
- 対象: `external-content.ts:174` の RSS 項目変換、`:226` の `selectKeepSet`、`:314` の同期ループ。
- 現状: 既存 YAML の重複は検出するが、RSS 内の重複は検出しない。
  同じ URL に異なるタイトルを持つ 2 項目を渡すと、同じファイルへの変更が 2 件でき、後の項目で上書きされる。
  ランキングの Map は重複を潰す一方、書き込みループは元の配列を使う。
- 改善案: 正規化 URL の一意な入力を作り、同一内容の重複の扱いを定義し、内容が競合する重複は変更前に拒否する。
- 完了条件: 同内容・異内容・フラグメントだけ異なる URL・項目順の入れ替えで結果を確認する。

### 03. 削除処理から RSS 取得を取り除く

- **P1 / 方針確定・PR #38 で実装済み（未マージ） / 再現済み**
- 対象: `external-content.ts:430` の `pruneContent`、`:226` の `selectKeepSet`。
- 現状: 削除時に全サービスの RSS を再取得し、まだ main に保存されていない項目も上限の枠を消費する。
  古い保存済み記事 20 件と、新しい未保存の RSS 記事 20 件があると、保存済み 20 件すべてが上限超過の削除候補になる。
- 確定方針: 削除処理は RSS を取得せず、実行時点の main に保存済みの YAML のみを対象にする（[ADR 0027](../adr/0027-prune-stored-content-without-rss.md)）。
  保存済みの公開日・比較用 URL で件数上限を適用し、保持対象のリンクの失効を確認する。
- 改善案: `pruneContent` から `feedLoader` と全サービスの RSS 取得を取り除き、保存済み項目だけで削除候補を選ぶ。
  同期側の既存データ・RSS の統合選定とは入力を分ける。
- 完了条件: RSS への通信が発生しない。同期失敗・未マージ・RSS にしかない項目や公開日の変更が、削除対象の選定に影響しない。
  保存済み項目の上限超過・リンク失効は削除し、リンク確認の判定保留と手動データは既存方針どおり扱う。

### 04. YAML の読み込み境界で実データを検証する

- **P1 / 入力境界の整理 / コード確認**
- 対象: `external-content.ts:189` の `readCollection`、既存の `src/content.config.ts`。
- 現状: `YAML.parse(...) as ContentData` は型の宣言だけで、値を検証しない。
  数値の日付、欠落したタイトル、不正 URL などが、ソートや URL 変換の途中で失敗する。ファイル名付きの入力エラーにならない。
- 改善案: ファイル名を含む実行時検証を読み込み直後に置く。Astro のスキーマと合わせる部分、同期専用の日付文字列の制約を整理する。
- 完了条件: 不正ファイルを読むと変更開始前に停止し、どのファイルのどの項目が不正か分かる。
  既存 YAML の許容形式を意図せず狭めない。

### 05. 新規追加時にもリンク確認の間隔を適用する

- **P1 / 通信制御の整理 / コード確認**
- 対象: `external-content.ts:318` の新規 URL 確認、`:400` の `verifyLinks`。
- 現状: 削除には 1 秒の間隔と最大 2 件の同時実行があるが、同期の新規 URL は応答が返るとすぐ次を確認する。
  計画の「同じサービスへの連続アクセスは 1 秒以上」と実装の適用範囲が一致しない。
- 改善案: 同期・削除から同じ通信スケジューラを利用する。
- 完了条件: 待機関数と時計を差し替え、速い応答・遅い応答でも開始間隔と同時実行数を確認する。

### 06. 実行全体の時間予算と未確認項目を表す

- **P1 / 運用条件の実装 / コード確認**
- 対象: `external-content.ts:351,400,430`、両ワークフローの `timeout-minutes: 10`。
- 現状: 個々の HTTP の 30 秒タイムアウトはあるが、処理全体の締切がない。
  1 URL につきリダイレクトを含め最大 6 リクエストとなり、30 URL を最大 2 件ずつ確認すると、通信だけで概算 45 分になり得る。
  runner の 10 分制限で強制終了され、計画にある「未確認は保持して次回へ」が処理結果として表現されない。
- 改善案: 共通の締切・残り時間・キャンセルを渡し、時間切れのリンクは未確認として保持する。
- 完了条件: 通常の timeout と全体の時間切れを区別し、途中まで確認した結果・未確認件数を報告する。

### 07. 手動フィールドの保持に関する計画文書をスキーマに合わせる

## 作業の分け方の案

以下の6段階をそれぞれ独立した PR として実装する。レビューしやすいように積み上げ、段階1のPRは `main` を base にし、段階2は段階1のブランチ、段階3は段階2のブランチという順で、段階6まで直前段階のブランチを base にする。先行 PR が main にマージされたら、必要に応じて後続ブランチを最新 main へ rebase し、PR の base を更新して差分を整理する。これは実行順とレビュー境界の案であり、新しい設計決定ではない。候補番号の主担当は一段階に一度だけ割り当てる。後段に主担当を置いた候補が前段の変更に関係する場合、前段ではその変更に必要な範囲のテストや受け渡しだけを行い、候補全体の完了とは扱わない。バグ修正は実装前に再現テストが失敗することを確認し、リファクタリングは維持する振る舞いのテストが実装前に成功することを確認する。変更後は同じテストと関連する既存テストを実行する。

### 1. URL 遷移と RSS 重複

- **主担当候補:** 01、02
- **前提:** なし。PR #29 のマージ済みコードを基準にする。
- **進め方:** 不具合ごとに再現するテストを先に追加し、実装前に失敗を確認する。URL 所有条件・遷移回数・相対 Location と、正規化 URL の重複・競合をそれぞれ固定してから修正する。
- **完了条件:** 候補 01・02 の記載ケースを回帰テストで確認し、競合入力や不正な遷移でファイル変更計画が作られない。関連する既存テストも成功する。
- **依存:** 段階 2 の削除リンク確認は、候補 01 の URL 判定を利用する場合にこの PR を先行させる。段階 3 以降もこの段階の URL 契約を維持する。

### 2. 保存済み削除、入力検証、main 上の保存データ

- **主担当候補:** 03、04
- **前提:** 段階 1。候補 03・07 の方針は ADR 0027 で確定済み。候補 03 は PR #38 で実装済み（未マージ）、07 の文書反映は段階 5 で扱う。
