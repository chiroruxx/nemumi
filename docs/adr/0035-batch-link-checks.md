# 0035. リンク確認を5件ずつのバッチで実行する

- **ステータス**: 承認
- **日付**: 2026-10-14

## 背景

[ADR 0029](0029-bound-content-network-execution.md) ではリンク確認を最大2件で並列実行し、同一サービスへの HTTP
リクエスト開始間隔を1秒以上にした。この制約を RSS 取得の再試行やリンクのリダイレクトにも適用するため、実行 context とリンク確認
runner にキュー、開始時刻、予約済みフラグが必要になっている。

保存上限は記事20件・登壇10件であり、サービスごとの開始時刻を管理するより、少量のリンクを固定バッチで確認する構成を選ぶ。短時間に同一サービスへ最大5件の確認が集中することを許容する。

## 決定

- リンク確認はサービスを問わず入力順に最大5件ずつ区切り、各バッチを `Promise.all`
  で並列実行する。全件が完了してから1秒待ち、次のバッチを開始する。最初のバッチ前と最後のバッチ後は待たない。
- バッチの単位はリンク確認とする。リダイレクトは同じ確認の中で順番に処理し、個々の HTTP リクエストにサービス別の開始間隔を設けない。RSS
  取得の再試行もサービス別の開始間隔を適用せず、従来の再試行待機と `Retry-After` に従う。
- サービス別キュー、開始時刻の管理、予約済みフラグを廃止する。実行 context は期限と AbortSignal の管理に絞る。
- 個別リクエストの30秒タイムアウトと既定8分の共通実行期限を継続する。待機時間だけで残り予算を使い切る場合は、次のバッチを開始しない。
- 確認が例外で失敗した場合は、その項目を `defer` として他の確認を続ける。全体期限までに結果を確定できなかった項目と後続バッチは未確認として報告する。期限後の結果は採用しない。
- 全体期限ではバッチ完了の待機も終了する。差し替えた確認関数が AbortSignal に応答しない場合も、runner は期限で終了する。
- 同期は未確認項目があれば部分適用せず、prune は期限までに確定した削除と件数上限による削除だけを適用する。
- テストで差し替える待機設定は、個別リクエストの間隔と区別できるバッチ間隔の名前にする。

## 結果

- 同時実行と間隔制御を単純なバッチループに集約し、実装とテストの分岐を減らせる。
- 同一サービスにも最大5件の確認が同時に始まる。リクエストごとの1秒間隔は保証しない。
- バッチ内の遅い確認が終わるまで次のバッチは開始しない。全体期限では確定済みの結果だけを利用する。
